## 1. 项目概述

### 1.1 核心目标

为基于 LangGraph 的电商异常处理多智能体工作流系统提供一个 **可视化运营管理平台**，让运营团队能够：

- **实时监控** AI 工作流的处理状态与全局健康度
- **高效完成** 人工审批 (HITL) 任务，缩短工单挂起时间
- **深度追溯** 每条工单的完整 AI 决策链路，做到每一步可解释
- **量化评估** AI 处理效能，驱动持续优化

### 1.2 核心场景

| 序号 | 场景名称 | 场景描述 |
|---|---|---|
| S1 | **晨检巡视** | 运营经理每日上班后，通过仪表盘快速了解前一日/过夜期间的 AI 处理概况，识别异常 |
| S2 | **待审工单处理** | 审批人打开审批中心，按优先级逐条审批被合规 Agent 标记为 ESCALATE 的工单 |
| S3 | **问题工单追溯** | 客户投诉处理结果不满，运营人员需追溯该工单的完整 AI 决策过程和政策依据 |
| S4 | **效能分析汇报** | 运营主管在周会上需要展示 AI 系统的处理量、成功率、成本和人工介入比例 |
| S5 | **策略文档管理** | 策略运营人员上传新的退货政策文档到向量库，使 AI 在后续决策中引用最新政策 |

### 1.3 业务痛点

| 痛点 | 现状 | 目标状态 |
|---|---|---|
| **HITL 响应慢** | 审批通知散落在 Slack 消息中，审批人需手动调用 API 恢复流程 | 统一审批队列，一键审批，实时恢复 |
| **AI 决策不透明** | 客服方案和合规审查结果仅存储在后端 State 中，无可视化界面 | 完整决策链路可视化，每步可展开查看输入/输出 |
| **运营无全局视角** | 系统运行状态需查看 LangSmith + 数据库 + Redis，信息分散 | 一个仪表盘聚合所有核心指标 |
| **策略更新滞后** | 更新政策需要工程师手动执行导入脚本 | 运营人员自助上传，自动索引入库 |

### 1.4 目标用户

| 用户角色 | 典型人物画像 | 核心诉求 | 使用频率 |
|---|---|---|---|
| **运营经理** | 管理 5-10 人客服团队，关注整体效率 | 全局监控、效能报表、异常预警 | 每日 |
| **HITL 审批人** | 资深客服或合规专员，拥有审批权限 | 快速审批、完整上下文、政策对照 | 每日多次 |
| **策略运营** | 负责维护公司退换货政策的运营人员 | 文档上传管理、版本控制 | 每周 |
| **技术负责人** | 系统开发/运维负责人 | Agent 调试、Trace 分析、错误排查 | 按需 |

### 2.2 场景 S2 详细流程：HITL 审批 (核心高频场景)

这是系统中使用频率最高、业务价值最大的操作链路，以下逐步描述从审批人收到通知到完成审批的完整过程：

```
步骤 1 ──── 审批人通过 Slack 通知或平台侧边栏红点感知到有待审工单
             ↓
步骤 2 ──── 点击侧边栏「审批中心」进入审批队列页
             系统展示所有 execution_status = SUSPENDED 的工单
             默认按「等待时长 ↓」排序，最久未处理的排在最前
             ↓
步骤 3 ──── 审批人点击某条工单，进入「审批详情页」
             页面加载：
             · 左侧面板：AI 客服 Agent 生成的解决方案 + 推理过程
             · 右侧面板：合规 Agent 引用的政策条款原文
             · 顶部区域：订单基础信息（脱敏后）
             · 底部区域：反思重写历史（如有）
             ↓
步骤 4 ──── 审批人阅读 AI 方案与政策条款，做出判断
             ↓
步骤 5A ─── [批准] 点击「批准」按钮
             · 按钮变为加载态，防止重复提交
             · 系统调用 POST /api/hitl/resume { decision: "APPROVED" }
             · LangGraph 恢复执行，Execution Agent 开始调用 Shopify/Klaviyo API
             · 页面显示 Toast：「审批已通过，工单已恢复执行」
             · 自动跳回审批队列，该工单从列表中移除
             ↓
步骤 5B ─── [驳回] 点击「驳回」按钮
             · 展开驳回批注输入框（必填，最少 10 字）
             · 审批人填写驳回理由
             · 点击「确认驳回」
             · 系统调用 POST /api/hitl/resume { decision: "REJECTED", notes: "..." }
             · 工单标记为 CANCELLED
             · 页面显示 Toast：「工单已驳回」
             · 自动跳回审批队列
```

### 2.3 场景 S3 详细流程：工单追溯

```
步骤 1 ──── 运营人员在「工单中心」页面搜索订单号
             ↓
步骤 2 ──── 在搜索结果中点击目标工单，进入「工单详情页」
             ↓
步骤 3 ──── 页面顶部显示横向节点时间线：
             PII脱敏 → 客服Agent → RAG检索 → 合规Agent → [HITL] → 执行Agent → END
             当前/最终停留的节点高亮
             ↓
步骤 4 ──── 点击任意节点（如「合规 Agent」），展开该节点的详细面板：
             · 输入：客服方案 + RAG 检索到的政策条款
             · 输出：APPROVED / REJECTED / ESCALATE + 审查理由
             · 运行时长、Token 消耗、使用的模型
             ↓
步骤 5 ──── 如需对比不同节点间的状态变化：
             点击「状态对比」切换为 Diff 视图
             左右并排显示两个节点执行后的 WorkflowState 差异
```

| **顶部栏** | 64px 高度，固定定位，z-index: 100 |
| **内容区内边距** | 24px (移动端 16px) |

- 主色 (Indigo) 仅用于可交互元素，不用于装饰
- 图表配色使用上述状态色的有序子集，确保一致性

| 动效场景 | 参数 | 说明 |
|---|---|---|
| 页面切换 | `opacity 200ms ease` | 淡入淡出 |
| 节点详情切换 | `opacity 150ms ease-out` | 面板内容平滑过渡 |

| 管道节点脉冲 | `scale 1→1.15→1, opacity 1→0.7→1` 2s infinite | 正在处理的节点持续脉冲 |

## 6. 设计理念：少即是多

本产品的 UI 设计遵循 **"少即是多" (Less is More)** 的核心理念，在每一个设计决策中贯彻克制原则：

### 6.1 信息架构：渐进式披露

- **一级信息 (一眼可见)：** 状态标签、关键数字 (金额、耗时)、操作按钮
- **二级信息 (一次点击)：** Agent 的输入输出详情、政策条款全文
- **三级信息 (主动探索)：** 状态快照 Diff、Token 统计、原始 JSON

用户不被信息淹没，而是按需深入。

### 6.2 视觉语言：留白即表达

- **卡片间距 24px**，内容区不拥挤
- **页面 90% 面积为白色/浅灰**，信息通过排版层级而非装饰元素建立
- **不使用渐变、阴影堆叠、图标装饰**——每一个视觉元素都承载功能
- **色彩仅用于状态语义**，不用于品牌强化或视觉点缀

### 6.3 交互原则：一个页面一个核心动作

| 页面 | 核心动作 | 其他元素的角色 |
|---|---|---|
| 仪表盘 | 感知系统状态 | KPI/图表都是对"状态"的不同维度表达 |
| 审批详情 | 批准或驳回 | AI 方案/政策对照都是辅助用户做出这一个决策 |
| 工单详情 | 理解 AI 决策链路 | 节点时间线是唯一的导航方式 |
| 策略库 | 上传/管理策略 | 卡片网格是浏览方式，上传是核心操作 |

### 6.4 组件克制

- **不使用** Tab 组件在详情页切换内容——用垂直滚动替代
- **不使用** 全局工具栏——操作按钮就近放置在相关内容旁
- **不使用** 多级弹窗嵌套——最多一层模态框
- **不使用** 侧抽屉——详情页用独立路由而非侧滑面板
- **表格列数 ≤ 7**——超过时砍掉最不重要的列

### 6.5 数据可视化：克制的图表

- 仪表盘仅 2 个图表 (管道可视化 + 状态分布)
- 分析报表仅 4 个图表 (趋势 + 分布 + Agent 耗时 + Token)
- 每张图表最多 5 个数据系列
- 不使用 3D 图表、仪表盘表盘、旋转动画等花哨效果
- 图表颜色直接复用状态色，无需额外色板
